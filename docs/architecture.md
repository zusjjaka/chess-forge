# Architecture

Сервис разделён на несколько слоёв, каждый из которых отвечает за свою область приложения.

## Structure

<pre>
/
├── <a href="#api">api/</a>
├── <a href="#core">core/</a>
├── <a href="#models">models/</a>
├── <a href="#schemas">schemas/</a>
├── <a href="#services">services/</a>
├── <a href="#repositories">repositories/</a>
├── <a href="#db">db/</a>
├── <a href="#alembic">alembic/</a>
├── <a href="#clients">clients/</a>
├── <a href="#keys">keys/</a>
├── <a href="#publishers">publishers/</a>
├── <a href="#exceptions">exceptions.py</a>
├── <a href="#tests">tests/</a>
└── <a href="#mainpy">main.py</a>
</pre>

---

## API

`api/` содержит HTTP API приложения.

Отвечает за:

* определение HTTP endpoints;
* обработку HTTP-запросов;
* валидацию входных данных через schemas;
* формирование HTTP-ответов;
* подключение dependencies.

API layer не содержит бизнес-логику.

---

## Core

`core/` содержит общие компоненты приложения и конфигурацию.

Используется различными частями сервиса и включает инфраструктурную логику, например:

* конфигурацию;
* security;
* JWT;
* общие зависимости;
* другие компоненты, не относящиеся к конкретному домену.

---

## Models

`models/` содержит ORM-модели базы данных.

Отвечает за описание структуры данных:

* таблицы;
* поля;
* связи;
* ограничения.

---

## Schemas

`schemas/` содержит Pydantic-схемы.

Используется для:

* валидации входных данных;
* сериализации ответов;
* описания API-контрактов;
* описания сообщений, передаваемых между сервисами.

Schemas описывают структуру данных и не являются ORM-моделями.

---

## Services

`services/` содержит бизнес-логику приложения.

Именно здесь реализуются основные операции и бизнес-правила сервиса.

Services не должны зависеть от HTTP API.

---

## Repositories

`repositories/` отвечает за доступ к данным.

Содержит логику взаимодействия с базой данных:

* получение данных;
* создание;
* изменение;
* удаление;
* выполнение запросов.

Repository отвечает за **доступ к данным**, но не за бизнес-правила.

---

## DB

`db/` содержит инфраструктуру базы данных.

Отвечает за:

* подключение к базе данных;
* создание database sessions;
* настройку SQLAlchemy;
* общие компоненты для работы с ORM.

---

## Alembic

`alembic/` содержит миграции базы данных.

Используется для:

* версионирования схемы базы данных;
* создания миграций при изменении ORM-моделей;
* применения миграций к базе данных;
* отката миграций при необходимости.

Миграции являются частью исходного кода проекта и хранятся в Git.

---

## Clients

`clients/` содержит клиентов для взаимодействия с внешними сервисами и инфраструктурными компонентами.

Clients инкапсулируют детали подключения и взаимодействия с внешними системами.

Например:

* RabbitMQ;
* SMTP;
* другие внешние API или сервисы.

Бизнес-логика не должна напрямую работать с низкоуровневым API внешних систем.

---

## Keys

`keys/` содержит ключи и связанные с ними компоненты, используемые для криптографических операций и работы с токенами.

Используется, например, для:

* JWT signing keys;
* JWT verification keys;
* других криптографических ключей.

Секретные ключи и приватные данные не должны храниться в Git. В репозитории хранятся только необходимые шаблоны или публичные компоненты.

---

## Publishers

`publishers/` отвечает за публикацию сообщений во внешние системы обмена сообщениями.

В Auth Service publishers используются для отправки сообщений в RabbitMQ.

Например, после регистрации пользователя сервис может:

1. создать код подтверждения;
2. сохранить его в базе данных;
3. сформировать сообщение;
4. передать сообщение publisher'у;
5. опубликовать сообщение в RabbitMQ.

Publisher отвечает за доставку сообщения в брокер по заданному контракту, но не содержит бизнес-логику формирования самого сценария.

---

## Exceptions

`exceptions.py` содержит кастомные исключения приложения.

Используются для описания ошибок, возникающих в бизнес-логике и application layer.

Исключения позволяют отделить возникновение ошибки от её представления в HTTP API.

Например:

* `UserAlreadyExistError`;
* `InvalidAccessTokenError`;
* `VerificationCodeInvalidError`.

HTTP-представление исключений выполняется через централизованный exception handler.

---

## Tests

`tests/` содержит автоматические тесты приложения.

Тесты проверяют корректность отдельных компонентов и взаимодействие между ними.

В зависимости от типа тестов могут использоваться:

* unit tests;
* integration tests;
* API tests.

---

## `main.py`

`main.py` является точкой входа приложения.

Отвечает за:

* создание FastAPI application;
* подключение роутеров;
* регистрацию middleware;
* регистрацию exception handlers;
* настройку lifecycle приложения.

Бизнес-логика в `main.py` не размещается.

---

# Dependency Flow

Основной поток выполнения HTTP-запроса:

<pre>
Client
  │
  ▼
API
  │
  ▼
Schemas
  │
  ▼
Services
  │
  ├──────────────► Repositories
  │                    │
  │                    ▼
  │                  Models
  │                    │
  │                    ▼
  │                 Database
  │
  └──────────────► Publishers
                       │
                       ▼
                    RabbitMQ
                       │
                       ▼
                  Other Services
</pre>

При этом:

* `Schemas` используются API для валидации и сериализации данных;
* `Services` содержат бизнес-логику и координируют работу компонентов;
* `Repositories` отвечают за доступ к базе данных;
* `Models` описывают структуру данных в базе;
* `Publishers` используются для отправки сообщений во внешние системы;
* `Clients` инкапсулируют взаимодействие с внешними сервисами;
* `Exceptions` используются для передачи ошибок между слоями без привязки бизнес-логики к HTTP.
