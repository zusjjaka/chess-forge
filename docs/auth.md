# Authentication

Система аутентификации отвечает за регистрацию пользователей, вход в аккаунт, выдачу и обновление токенов, а также завершение пользовательских сессий.

В проекте используется схема **JWT Access Token + Refresh Token**.

## Authentication Flow

```text
Client
  │
  ├── Register ──────────────► Auth Service
  │                              │
  │                              ▼
  │                           PostgreSQL
  │
  ├── Login ─────────────────► Auth Service
  │                              │
  │                              ├── Access Token
  │                              └── Refresh Token
  │
  ├── API request
  │      └── Authorization: Bearer <access_token>
  │
  └── Access токен истёк или потерян
         │
         ▼
      /refresh
         │
         ├── Refresh Token
         ▼
     Auth Service
         │
         ├── валидация refresh токена
         ├── ротация refresh токена
         ├── получения нового access токена
         └── получение нового рефреш токена
```

---

## Registration

При регистрации клиент отправляет необходимые данные пользователя в Auth Service.

Auth Service:

1. Проверяет данные запроса.
2. Проверяет, что пользователь с указанным email/username ещё не существует.
3. Хэширует пароль с использованием [password hashing algorithm](/docs/security.md#1-password-hashing).
4. Создаёт пользователя в [`auth_db`](/docs/database.md#auth-service--auth_db).
5. Возвращает результат регистрации.

Пароль никогда не хранится в исходном виде. В базе данных хранится только `password_hash`.

---

## Login

При входе пользователь отправляет email/username и пароль.

Auth Service:

1. Находит пользователя в `auth_db`.
2. Проверяет переданный пароль против `password_hash`.
3. Создаёт Access Token.
4. Создаёт Refresh Token.
5. Сохраняет хэш Refresh Token в `refresh_tokens`.
6. Возвращает токены клиенту.

Если credentials неверны, сервер возвращает `401 Unauthorized`.

---

# Access Token

Access Token представляет собой **JWT**, подписанный с использованием алгоритма **RS256**.

Пример payload:

```json
{
  "sub": "user_id",
  "iat": 1755350000,
  "exp": 1755350600,
  "jti": "unique-token-id"
}
```

### RS256

Для создания JWT используется приватный RSA-ключ:

```text
Private Key
     │
     ▼
 Sign JWT
     │
     ▼
Access Token
```

Другие сервисы используют публичный RSA-ключ для проверки подписи:

```text
Access Token
     │
     ▼
Public Key
     │
     ▼
Signature valid?
```

Приватный ключ не передаётся другим сервисам.

### Lifetime

Access токен имеет короткий срок жизни. Это уменьшает последствия его компрометации.

После истечения Access Token клиент должен получить новый токен через Refresh токен.

Access токен не сохраняются в базе данных. Их валидность определяется по подписи, `exp` и т.д.

---

# Refresh Token

Refresh токен не является JWT.

Это криптографически случайная строка, сгенерированная сервером.

Например:

```text
random bytes
     │
     ▼
secure random token
     │
     ▼
Refresh Token
```

В базе данных **не хранится сам Refresh токен**.

Сохраняется только его SHA-256 хэш:

```text
Refresh Token
      │
      ▼
    SHA-256
      │
      ▼
  token_hash
```

При получении Refresh токена сервер повторно вычисляет его хэш и ищет соответствующую запись в `refresh_tokens`.

---

# Refresh Token Storage

Для каждого Refresh Token хранится информация о его состоянии и сессии.

Основные поля:

| Поле                   | Тип           | Описание                                                                                        |
| ---------------------- | ------------- | ----------------------------------------------------------------------------------------------- |
| `id`                   | `uuid`        | Уникальный идентификатор refresh-токена.                                                        |
| `user_id`              | `uuid`        | Идентификатор пользователя, которому принадлежит токен.                                         |
| `hashed_refresh_token` | `bytea`       | Хэш refresh-токена в бинарном представлении.                                                    |
| `ip_addr`              | `varchar(39)` | IP-адрес, с которого был создан токен. Поддерживает IPv4 и IPv6.                                |
| `user_agent`           | `text`        | User-Agent клиента, использовавшего токен.                                                      |
| `is_active`            | `boolean`     | Показывает, является ли токен активным.                                                         |
| `expires_at`           | `timestamptz` | Время истечения действия токена.                                                                |
| `created_at`           | `timestamptz` | Время создания токена.                                                                          |
| `revoked_at`           | `timestamptz` | Время отзыва токена. `NULL`, если токен не был отозван.                                         |
| `replaced_by`          | `uuid`        | Идентификатор токена, которым был заменён текущий токен. `NULL`, если замены не было.           |
| `family_id`            | `uuid`        | Идентификатор семейства refresh-токенов, используемый для отслеживания цепочки ротации токенов. |

# Refresh Token Rotation

При каждом успешном обновлении Access токена старый Refresh токен инвалидируется и создаётся новый.

Например:

```text
RT1 → RT2 → RT3 → RT4
```

После использования `RT1`:

```text
RT1: revoked
RT2: active
```

После использования `RT2`:

```text
RT1: revoked
RT2: revoked
RT3: active
```

Таким образом, каждый Refresh токен предназначен для **однократного использования**.

Rotation позволяет обнаруживать повторное использование уже отозванного Refresh Token.

---

# Refresh Token Reuse Detection

Если клиент отправляет Refresh Token, который уже был использован и отозван, сервер рассматривает это как потенциальную компрометацию токена.

Например:

```text
RT1 → RT2 → RT3
      ↑
      └── повторное использование
```

Сервер находит `RT2` и видит, что он уже отозван.

В этом случае инвалидируется вся `family_id`:

```text
RT1  revoked
RT2  revoked
RT3  revoked
```

Пользователь должен пройти повторную аутентификацию.

Это позволяет ограничить последствия кражи Refresh Token и обнаружить его повторное использование.

---

# Token Expiration

Access токен имеет короткий lifetime, поэтому его истечение является нормальной частью работы системы.

Refresh токен имеет значительно больший lifetime.

Если Refresh токен истёк:

```text
Client
  │
  │ expired refresh token
  ▼
Auth Service
  │
  ▼
401 Unauthorized
```

Пользователь должен выполнить повторный login.

---

# Logout

При выходе из аккаунта текущий Refresh Token отзывается в `auth_db`.

Access токен при этом не обязательно удалять, т.к. Access токены не хранятся сервером.

Если Access токен ещё не истёк, он технически остаётся действительным до окончания своего lifetime.

Поэтому короткий lifetime Access токена уменьшает период, в течение которого украденный Access Token может использоваться после logout.

Так же access токены на стороне фронтенда хранятся в замыкании функций, что приведёт к его исчезновению при обновлении страницы.

# Token Storage

Refresh токен храниться на клиенте таким образом, что JavaScript не имеет к нему доступа.

Для web-клиента используется:

```text
HttpOnly
Secure - для production
SameSite: Strict
Path=/api/v1/auth/
```

cookie.

`HttpOnly` предотвращает прямой доступ к Refresh токен из JavaScript, а `Secure` ограничивает его передачу защищёнными HTTPS-соединениями.

Access токен рекомендуется хранить только в памяти клиентского приложения и передавать API через:

```http
Authorization: Bearer <access_token>
```
