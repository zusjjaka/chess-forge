# Infrastructure

Документ описывает инфраструктуру Chess Forge, окружение разработки и взаимодействие основных инфраструктурных компонентов.

## Python

* Версия Python.
* Способ управления зависимостями.
* Основные runtime-зависимости.
* Development-зависимости.
* Команды для запуска приложения и тестов.

## `pyproject.toml`

`pyproject.toml` является основной конфигурацией Python-проекта.

Содержит:

* метаданные проекта;
* зависимости;
* development-зависимости;
* конфигурацию инструментов разработки;
* настройки тестирования;
* настройки линтера и форматтера;
* настройки type checking.

## Environment Variables

Конфигурация приложения передаётся через переменные окружения.

`.env` используется для локального окружения разработки и не хранится в репозитории.

Основные категории настроек:

* application;
* PostgreSQL;
* Redis;
* RabbitMQ;
* authentication;
* external services;
* development environment.

Секреты и credentials не должны храниться в Git.

## Docker

Docker используется для изоляции приложения и инфраструктурных компонентов.

Основные задачи:

* одинаковое окружение разработки;
* изоляция зависимостей;
* воспроизводимый запуск сервисов;
* подготовка окружения, близкого к production.

## Docker Compose

Docker Compose используется для локального запуска нескольких взаимосвязанных сервисов.

Планируемая структура:

```text
Docker Compose
├── API
├── PostgreSQL
├── Redis
├── RabbitMQ
└── ...
```

Сервисы взаимодействуют между собой через внутреннюю Docker network.

## PostgreSQL

PostgreSQL используется как основная реляционная база данных приложения.

Используется для хранения:

* пользователей;
* репертуаров;
* линий;
* тренировочных сессий;
* тренировочных ходов;
* других транзакционных данных.

Данные PostgreSQL должны сохраняться между перезапусками контейнера через Docker volume.

## Redis

Redis используется как быстрое in-memory хранилище.

Основные сценарии:

* кэширование часто запрашиваемых данных;
* временные данные;
* TTL-based storage;
* оптимизация проверок уникальности тегов;
* другие операции, которым не требуется постоянное хранение в PostgreSQL.

Redis не является источником истины для запросов, но он оптимизирует их.

## Networking

Компоненты приложения взаимодействуют через внутреннюю сеть инфраструктуры.

Пример:

```text
Client
  │
  ▼
API
  ├── PostgreSQL
  ├── Redis
  └── RabbitMQ
```

В Docker Compose сервисы обращаются друг к другу по именам сервисов внутри Docker network.

Публичными должны быть только необходимые для клиента порты.

## Development Environment

Локальное окружение должно позволять запустить проект без ручной установки всех инфраструктурных компонентов.

Основной workflow:

```text
Clone repository
      ↓
Install Python dependencies
      ↓
Configure .env
      ↓
Start infrastructure
      ↓
Run database migrations
      ↓
Start application
      ↓
Run tests
```

Инструкции по запуску и необходимые команды будут поддерживаться в актуальном состоянии вместе с изменениями инфраструктуры в [README.md](../README.md).

## CI/CD

CI/CD используется для автоматической проверки изменений.

Планируемый pipeline:

```text
Push / Pull Request
        ↓
Lint
        ↓
Type checking
        ↓
Tests
        ↓
Build
        ↓
Deployment
```

Конкретная конфигурация deployment зависит от целевого окружения продукта.

## Monitoring

Для мониторинга приложения планируется использовать Prometheus и Grafana.

А для логирования ошибок - Sentry SDK.

Архитектура:

```text
Application
     │
     ▼
Prometheus
     │
     ▼
Grafana
```

Планируемые метрики:

* CPU;
* memory;
* request rate;
* request latency;
* error rate;
* database metrics;
* Redis metrics;
* engine worker metrics.

Monitoring будет использоваться не только для production observability, но и для анализа поведения системы под нагрузкой.

## Future Infrastructure

Возможные будущие инфраструктурные компоненты:

* S3-compatible object storage;
* horizontal scaling;
* дополнительные engine workers;
* load testing с помощью Locust;
* Prometheus + Grafana;
* другие инструменты при появлении соответствующих требований.

Инфраструктурные технологии не добавляются без необходимости: каждое дополнительное решение должно иметь конкретную задачу или измеримый эффект.
